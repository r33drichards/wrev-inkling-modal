# Production plan: Wrev on Modal

**Status:** Proposed. This document does not deploy an app, register a webhook, or change the Railway worker. [PR #1](https://github.com/r33drichards/wrev-inkling-modal/pull/1) is an acceptance experiment, not a dependency of this plan.

## What we have, and what we don't

The [B200 run](https://modal.com/apps/r33drichards/main/ap-DbkSFMRAqN4EF60Smubzv3) used a synthesized, signed delivery for a real PR. It demonstrated a pinned diff read via the Go queue, Wasmtime/WASIp2, Wrev's QuickJS tools, and Inkling on one B200. It persisted a valid empty findings result after 19 tool calls in 20 model turns. The [GitHub start-to-result comment](https://github.com/r33drichards/webhook/pull/11#issuecomment-7207583860) was exercised separately. It did not show real delivery, production auth, durable restart, automatic write-back, or detection of a known bug. The test's temporary endpoint patch, local GitHub CLI credentials, SQLite state, and one-shot Modal entrypoint are not the service.

## Target deployment

```text
GitHub App (pull_request: labeled / unlabeled, synchronize, closed)
  -> public Modal CPU Web Function -> Go /github/webhook
       verify signature; transactionally store delivery + state; return 202
  -> Postgres: queue, active revisions, leases, results, comment outbox
       -> Modal CPU job: pin evidence -> Wasmtime / Wrev -> validate findings
            -> trusted host gateway -> authenticated Modal B200 / vLLM / Inkling
       -> dedicated host-side publisher: GitHub App token -> start/edit comment
```

- **Ingress:** Run the vendored Go listener in a separately deployed Modal CPU app using [a web server endpoint](https://modal.com/docs/guide/webhooks). Bind a stable HTTPS URL. Check a size cap and HMAC-SHA256 over the raw body before parsing, then verify installation/repository allowlists and event/action. Exact label matching; draft PRs are included. Route installation IDs from the authenticated event against configured allowlists. No GitHub token mint, workspace fetch, or GPU work in the HTTP request. Acknowledge a relevant delivery only after its Postgres transaction commits; ignore irrelevant events and acknowledge duplicates without new work. A failed commit returns a retryable 5xx; do not assume GitHub retries automatically. Build an operator redelivery runbook and alerts based on [GitHub's delivery guidance](https://docs.github.com/en/webhooks/using-webhooks/best-practices-for-using-webhooks).
- **Durable work:** Use managed Postgres, with separate staging/prod databases and roles (Neon is a candidate), TLS, low pool limits, migrations and backup/restore. Extract an interface around the existing SQLite-backed worker in `webhook/review_service.go`; reuse validation, label semantics and evidence preparation rather than forking them into Python. Unique receipt by installation/repo/delivery ID. Unique active job by repo/PR/head/activation; verify current state from GitHub after claim, not from webhook arrival order. Re-adding after removal creates a new activation; a new head supersedes the old review and gets a new job if the label is still active. Handle close as cancellation. A conditional claim with a lease and fencing token ensures that an expired worker can't publish. Initially retry from immutable evidence rather than promise partial inference resume. Acknowledge after commit, then best-effort wake a CPU drainer; a scheduled sweeper recovers missed wakeups, expired leases, and pending outbox rows. Alert on oldest job and dead-letter exhaustion. Test that rollout/restart does not lose accepted work.
- **Review process:** Package a pinned Wasmtime build and Wrev component in the CPU job image. Pin and verify exact base/head SHAs, stage only needed evidence, and set evidence size, depth and time budgets. Treat PR text/data as untrusted. Do not run PR code, builds, or shell commands. Limit the guest to job-scoped evidence and scratch paths; no GitHub/DB credentials, inherited environment, or arbitrary network. Permit WASI HTTP only to the trusted model gateway. Add explicit upstreamable provider config and a streaming Responses contract rather than rewriting source at runtime. Gateway injects Modal credentials and refuses unexpected destinations and redirects. Validate findings schema and file/line references, bound bytes and redact output. Commit a typed outcome before publication. Reserve a final schema-constrained turn once the required evidence has been read; missing evidence, timeout, exhausted budget or invalid schema fails explicitly, never produces a clean review.
- **Inference:** Deploy a separate authenticated Modal B200 function (TP1), pinned Inkling 2 Mini checkpoint and pinned vLLM image digest with the tested Inkling parsers/DSpark recipe. Keep weights on a private Modal Volume; never put the queue on that volume. Use zero minimum GPUs, one maximum and a measured idle window initially. Limit queued/in-flight reviews at the caller. Keep `--max-model-len` and `--max-num-seqs` unset as requested; gate accepted request sizes in the gateway and measure the effective server limits under load. Carry forward the 180-second model timeout and 100 MiB script memory and output settings, with separate, smaller context/response/public-comment budgets. Measure cold start independently from request timeout. Test a cold-start/readiness path before consuming review attempts. Disable GPU spawning with a kill switch; don't silently fail over to a different model. [Modal vLLM reference](https://modal.com/docs/examples/vllm_inference) · [Inkling B200 recipe](https://recipes.vllm.ai/thinkingmachines/Inkling-2-Mini?hardware=b200&features=reasoning%2Cspec_decoding%2Ctool_calling).

## Comment contract

1. After the first successful job claim and GitHub state check, write a comment intent to the outbox. In comment-enabled mode, post **Wrev review started** with short head SHA before requesting the model. Do not wait for the GPU to warm up to post it. Stage with writes disabled until explicitly enabled. Keep the label as the user-controlled trigger; don't auto-remove it at launch.
2. Publisher uses a short-lived installation token with only the required PR/comment access; evidence uses a separately scoped read token. Persist comment ID and a deterministic per-job marker. If a POST times out or succeeds before the ID is saved, reconcile by looking for the marker on a comment from the app before retrying; serialize publication per PR. Reconcile rate limits and ambiguous success, and test replay rather than relying on exactly-once HTTP semantics.
3. Edit that same comment for completion, failure, supersession or cancellation. Re-fetch current PR state before publishing findings; do not publish old findings on a moved head or removed label. Make comments explicitly revision-scoped because GitHub state can change after the read. The next event reconciles a superseded comment. Escape untrusted text and suppress model-provided mentions. Never publish secrets, raw prompts or internal errors. Hold the review if a start comment can't be posted in comment-enabled mode; retries must recover the same intent.

## Build and release gates

| PR / stage | Exit criteria |
| --- | --- |
| 1. Durable Go ingress and runner lifecycle | CPU integration suite uses real Postgres and a mock GitHub server: signed request, malformed/oversize body, replay, different delivery IDs for same event, wrong repo, close, unlabel/re-label, head move, stale/out-of-order event, crash/reclaim and DB outage. Multi-worker tests prove old claim cannot finish. Only committed enqueue gets 2xx. |
| 2. Wasmtime, provider and publisher | Use the production images against mock GitHub and mock model. Verify stdout schema, replay/partial SSE and call IDs, budget exhaustion and credential isolation. Kill the worker mid-review and the publisher between POST and storing the ID. Assert one start comment, edited in place; assert cancellation and stale-head suppress findings. Confirm mock tests make no GPU calls. |
| 3. Deployed staging with a real GitHub App | Separate Modal env, DB, secrets and test-only app installation. Apply/remove a staging label on actual fixture PRs; exercise delivery from GitHub, replay from GitHub's history, cold-start, and deploy/restart while a job is active. Run one clean PR and one seeded non-security correctness bug, with an expected finding and line. Verify the app authors the start comment and edits it through the actual production code path, and no write credential reaches the guest or GPU. |
| 4. Production canary | Start single-repo and one B200 cap; shadow with comments disabled using a separate label, then enable comments for that repo. Verify accepted deliveries survive release, no duplicate Railway/Modal reviews, and all jobs reach an explainable outcome. Cut over the normal label only after approval and sign-off on staging/canary evidence. Expand by repo explicitly. |

**Proposed canary gates:** 20 real GitHub deliveries (including duplicates/cancels), p95 webhook acknowledgment under 2 s and none above 8 s, zero lost acknowledged deliveries, duplicate/superseded findings comments or secret leaks. Inject worker termination and confirm reclaim within two sweeper intervals after lease expiration. Record queue delay, start-comment delay, cold/warm total review latency, success/failure rate, billed GPU seconds per completed review and spend per day. Publish the observed numbers and agree latency/spend thresholds before expanding; the single B200 test is not a baseline for an SLO. Keep a separate known-bug/clean check for quality. Have staging demonstrate both a cold path and a warm path under end-to-end worker deadlines.

## Operations and rollback

- Deploy ingress, worker and inference independently with pinned artifact/image/model hashes and a release manifest. Use separate Modal environments, secret names and GitHub App instances or installations. CI runs CPU checks by default; GPU staging is explicitly triggered. Use forward/backward-compatible migrations and keep backups with a tested restore. Keep a worker/publisher pause and a model kill switch independent of app deploys.
- Trace GitHub delivery ID -> job ID -> exact SHA -> Modal invocation -> comment ID. Log structured state transitions and sanitized errors, never webhook bodies, diff content, secrets or model reasoning. Alert for signature failures, stuck leases/outbox, growing queue, elevated failures, and GPU budget. Maintain operator instructions for redelivery, retry by job ID, restore, rotation and cleanup/retention.
- Keep Railway untouched during staging. At cutover control ownership per repo/label so only one publisher handles it. For rollback, disable Modal claims and publishing first, fence or cancel active attempts, and account for already-accepted jobs before restoring Railway ownership. Route new events back to Railway only after verifying exclusivity. Reconcile current GitHub label/head state and delivery history to recover events during the switch; never blindly replay into both. Keep the previous Modal artifacts deployable without a destructive DB rollback.

**Release sign-off:** confirm the first canary repo, monthly GPU budget and evidence retention; record app installation scopes, test results, current route owner, release IDs, and a rollback drill. This planning PR authorizes no deployment or GitHub App changes.
